# 南坡之窗整体系统设计与开发计划

> 文档版本：V1.0  
> 编制日期：2026-08-29  
> 适用范围：南坡之窗公开门户、农户经营台、村庄运营后台及 Spring Boot 服务端  
> 项目状态：高保真原型已完成，生产级业务能力待按本计划实现

## 1. 项目背景

南坡之窗面向河南省焦作市修武县大南坡村，统一展示村庄介绍、到访路线、周边百公里旅行、民宿、农产品、游玩采摘和村民真实生产过程。

系统重点解决以下问题：

1. 农业从业者表达能力有限，难以持续整理产品卖点和真实生产故事。
2. 农户缺少独立电商收款、订单管理、发货和售后能力。
3. 村庄内容分散，游客无法在一个入口完成“了解—规划—咨询—购买”。
4. 图片、视频、语音和生产记录缺少统一归档、审核和公开渠道。
5. 村庄运营方需要统一管理内容、核款、备货、发货和对外联系方式。

## 2. 建设目标

### 2.1 产品目标

- 建立一个移动端优先、多端适配的“南坡之窗”公开门户。
- 为每个认证农户提供低门槛的图文、视频、语音生产记录入口。
- 使用语音识别和生成式 AI，把农户口述整理为有来源、不过度营销的对外内容。
- 建立商品下单、收款码展示、人工核款、备货、发货、物流和完成闭环。
- 为民宿、农产品、采摘项目、景点、路线和联系方式提供统一后台配置能力。
- 最终以前后端单仓、一个 Spring Boot JAR、一个服务端口的方式交付。

### 2.2 V1 成功指标

- 认证农户可以在 3 分钟内通过语音和照片提交一条生产记录。
- 80% 以上的生产记录可由 AI 生成可用初稿，并由农户或管理员确认后发布。
- 所有公开农产品都能追溯到农户、地块和已审核生产记录。
- 订单的每次状态变化均有操作人、时间和备注记录。
- 公开页面在主流手机、平板和桌面浏览器上可完整使用。
- 单体服务可以通过 `java -jar` 或 Docker 在端口 `8080` 启动。

### 2.3 V1 暂不包含

- 平台内在线支付、自动分账和代收结算。
- 自动确认微信或支付宝到账。
- 实时房态、酒店 PMS 或 OTA 深度对接。
- 自建地图导航和实时路况能力。
- 农产品质量认证、保险或检测报告的法律背书。

## 3. 当前原型基线

### 3.1 已在前端原型中展示

- 村庄首页、村庄故事和文化空间。
- 自驾、高铁换乘、市区公交三类出行指南。
- 100 公里内景点卡片、地图外链和半日/一日/两日路线规划。
- 民宿、农产品、游玩采摘的分页展示。
- 图片、视频预览和公开内容卡片。
- 农产品真实生产过程时间线。
- 客户填写收货信息、查看演示收款码、提交转账完成声明。
- 农户生产记录、图片/视频上传入口、语音入口和 AI 文案演示。
- 后台运营总览、内容上架、生产记录审核、订单核款和发货状态流。

### 3.2 已具备的工程能力

- `frontend/`：React + Vite 前端工程。
- `backend/`：Java 21 + Spring Boot 后端工程。
- 前后端开发阶段可分别启动。
- Maven 集成构建会自动安装 Node、执行 `npm ci`、构建前端并打入后端 JAR。
- Spring Boot 当前提供 `/api/health` 健康检查和静态页面托管。
- Docker 最终仅暴露后端端口 `8080`。

### 3.3 尚未实现的生产能力

- 真实账号、登录、角色权限和农户认证。
- 数据库、对象存储、业务 API 和后台持久化。
- 真实语音识别、AI 内容生成和人工审核链路。
- 真实订单、核款凭证、物流、通知和操作日志。
- 图片/视频上传、转码、鉴黄、病毒扫描和容量治理。
- 配置中心、监控告警、备份恢复和生产环境部署。

## 4. 用户角色与权限

| 角色 | 主要职责 | 数据范围 |
| --- | --- | --- |
| 游客 | 浏览村庄、路线、景点、民宿、采摘和农产品 | 仅公开数据 |
| 客户 | 提交订单、报告已转账、查询订单和物流 | 本人订单 |
| 农户 | 管理本人农品、地块、生产记录、媒体和 AI 文案 | 本人及被授权数据 |
| 内容运营 | 编辑村庄、路线、景点、民宿、采摘和联系方式 | 村庄公开内容 |
| 审核员 | 审核农户身份、生产记录、媒体和 AI 文案 | 审核队列 |
| 订单运营 | 核对收款、通知备货、录入物流、处理售后 | 全部订单，不含系统配置 |
| 超级管理员 | 用户、角色、收款码、字典、系统配置和审计 | 全部数据 |

权限模型采用 RBAC，并增加农户数据归属校验。任何“管理员可访问”的接口都不能只依赖前端隐藏按钮。

## 5. 功能范围设计

## 5.1 公开门户

### 村庄首页

- 村庄品牌、位置、简介、文化空间和重点数据。
- 推荐到访季节、一日游建议和行前提醒。
- 村庄联系电话、地址、营业时间和地图入口。
- 图文、视频、分享卡片和 SEO 元数据。

### 出行指南

- 自驾、高铁换乘、公交三类路线。
- 起点、终点、预计时长、途经节点和注意事项。
- 后台设置推荐路线、有效期和信息来源。
- 过期提醒和人工复核时间。

### 百公里周边游

- 景点名称、分类、距离、预计车程、亮点、封面图和地图外链。
- 半日、一日、两日等主题路线。
- 路线途经点、建议时间、适合人群、注意事项和收藏。
- 景点和路线独立上下线，不影响历史订单。

### 民宿

- 民宿列表、分页、详情、图集、视频、容纳人数和价格说明。
- 联系电话、咨询入口、服务设施、入住须知和地理位置。
- V1 采用咨询预约，不做实时房态和在线订房。

### 游玩与采摘

- 项目列表、分页、季节、时长、价格、名额和预约说明。
- 图集、视频、开放日期、适龄提示和安全须知。
- 项目咨询或预约申请，后台确认后通知客户。

### 农产品商城

- 商品列表、分页、分类、季节、价格区间和上下架状态。
- 商品详情、SKU、库存说明、农户信息、产地和生产过程。
- “看过程”进入可追溯时间线，“购买”进入订单流程。
- 对外分享链接可指向单个商品或农户公开页。

### 农户/产品公开页

- 农户简介、认证状态、地块、在售农品和生产记录。
- AI 整理的故事必须标记来源记录和最后审核时间。
- 微信分享文案、二维码和分享卡片。
- 支持管理员下线敏感或失实内容。

## 5.2 客户订单流程

1. 客户选择商品和 SKU。
2. 填写收货人、电话、地址和备注。
3. 后端创建唯一订单号并锁定价格快照。
4. 页面展示当前有效的村庄统一收款码、金额和转账备注规则。
5. 客户点击“我已完成转账”，可选上传转账凭证。
6. 订单运营人工核对实际到账。
7. 确认到账后通知农户备货。
8. 备货完成后由运营录入物流公司和单号。
9. 客户查看运输状态，最终确认完成或由系统超时完成。

关键约束：

- 收款码只展示，不在系统内声明自动到账。
- 金额、收款码版本和订单快照必须留存，避免后续配置变化影响历史订单。
- “客户报告已转账”不等同于“后台确认到账”。
- 核款、取消、退款、修改地址、发货都要写入操作日志。

## 5.3 农户经营台

### 农户认证

- 手机号登录或由村级管理员创建账号。
- 身份信息、村组、联系人、认证状态和授权范围。
- 一个农户可管理多个地块和多个农品。

### 地块与农品

- 地块编号、位置描述、面积、主要作物和现场图片。
- 农品名称、品类、规格、价格、库存说明、封面和销售状态。
- 农品与地块、生产记录建立关联。

### 真实生产记录

- 生产阶段：整地、播种、施肥、生长、采收、加工、包装等。
- 支持文字、照片、视频、语音和拍摄时间。
- 原始文件、转码文件、语音转写和编辑后文本分别保存。
- 提交时确认真实性声明，进入村级审核。
- 审核通过后才可出现在公开时间线和 AI 文案素材中。

### 语音交互

- 大按钮录音，支持开始、暂停、重录和试听。
- 语音转文字后用简单问题补充缺失信息，例如时间、地块、作物和生产动作。
- 支持文字朗读，便于识字能力有限的用户确认内容。
- 网络不稳定时先在本地保留录音，恢复后续传。

### AI 对外表达助手

- 根据已审核生产记录生成商品介绍、农户故事和微信分享文案。
- 显示引用了多少条记录、哪些字段仍不完整。
- 农户可以试听、修改、重新生成、复制或提交审核。
- 生成内容不得虚构产量、认证、功效、农药使用或质量结论。

### 备货协同

- 查看分配给本人的待备货订单。
- 确认接单、预计备货时间、备货完成和异常原因。
- 不向农户开放核款与全量客户数据。

## 5.4 村庄运营后台

### 运营总览

- 待核款、待发货、待审核、异常订单和内容更新提醒。
- 订单趋势、商品意向、公开内容数量和农户活跃情况。
- 今日待办与最近操作动态。

### 内容管理

- 村庄介绍、文化空间、出行路线和联系方式。
- 景点、旅行路线、民宿、游玩采摘和活动。
- 草稿、待审核、已发布、已下线和归档。
- 排序、推荐位、发布时间、失效时间和预览。

### 农户与生产记录审核

- 农户认证、地块审核、农品审核和生产记录审核。
- 查看原始图片、视频、语音、转写文本和 AI 生成内容。
- 通过、驳回、退回补充和强制下线。
- 驳回必须选择原因并通知农户。

### 订单与发货

- 按状态、日期、商品、客户和农户检索。
- 核款、取消、确认备货、录入物流、完成和退款登记。
- 敏感信息脱敏展示，必要时按权限查看完整信息。
- 状态操作必须幂等，并记录操作前后值。

### 收款码与联系配置

- 收款主体、收款码图片、启用时间、停用时间和版本。
- 访客服务、民宿咨询、采摘预约和售后联系方式。
- 历史订单始终引用创建订单时的收款配置快照。

### 系统管理

- 用户、角色、权限和数据范围。
- 字典、内容分类、媒体限制和 AI 模板。
- 登录日志、操作日志、异常日志和导出记录。

## 5.5 媒体中心

- 支持 JPG、PNG、WebP、MP4、MOV、M4A、MP3、WAV 等常见格式。
- 客户端直传对象存储，后端签发临时上传凭证。
- 图片压缩、水印、缩略图和 EXIF 隐私清理。
- 视频转码、封面截取、时长限制和播放兼容格式。
- 语音文件转写后仍保留原始音频，设置访问权限和保留周期。
- 文件类型白名单、大小限制、病毒扫描、鉴黄和违规内容审核。

## 6. 业务状态设计

## 6.1 内容状态

```text
DRAFT 草稿
  → PENDING_REVIEW 待审核
  → PUBLISHED 已发布
  → OFFLINE 已下线
  → ARCHIVED 已归档

PENDING_REVIEW → REJECTED 已驳回 → DRAFT
PUBLISHED → PENDING_REVIEW（重大修改需重新审核）
```

适用于农品、生产记录、民宿、采摘项目、景点、路线和 AI 文案。

## 6.2 订单状态

```text
CREATED 已创建
  → PAYMENT_PENDING 待转账
  → PAYMENT_REPORTED 客户已报告转账
  → PAID 后台已确认到账
  → PREPARING 农户备货中
  → READY_TO_SHIP 待发货
  → SHIPPED 运输中
  → COMPLETED 已完成
```

异常分支：

```text
CREATED / PAYMENT_PENDING → CANCELLED 已取消
PAYMENT_REPORTED → PAYMENT_PENDING 核款未找到，退回核对
PAID / PREPARING / READY_TO_SHIP → REFUND_PENDING 退款处理中
REFUND_PENDING → REFUNDED 已退款
SHIPPED → AFTER_SALE 售后处理中
```

订单状态只能通过后端命令接口迁移，禁止前端直接提交任意目标状态。

## 6.3 媒体状态

```text
CREATED → UPLOADING → UPLOADED → PROCESSING → READY
                                      └→ FAILED
READY → BLOCKED（审核或安全检测不通过）
```

## 7. 总体技术架构

```text
浏览器 / 手机 / 平板
        │
        ▼
Spring Boot :8080
  ├─ 静态资源：React + Vite 构建产物
  ├─ /api/public/** 公开查询
  ├─ /api/customer/** 客户订单
  ├─ /api/farmer/** 农户经营台
  ├─ /api/admin/** 运营后台
  └─ /actuator/** 健康与监控
        │
        ├─ MySQL：业务数据、状态与审计
        ├─ Redis：验证码、会话、限流、短期任务状态（可选）
        ├─ 对象存储：图片、视频、语音和凭证
        ├─ AI 网关：语音识别、文本生成、文字转语音
        ├─ 短信/消息服务：验证码和状态通知
        └─ 物流查询服务（V1 可先人工录入）
```

```text

├─ infrastructure/

├─ config/
└─ common/              # 错误码、分页、审计等
```

### 7.3 数据库与迁移

- 推荐 MySQL 8，字符集统一为 `utf8mb4`。
- 使用 Flyway 管理数据库变更，迁移脚本随代码提交。
- 金额使用 `DECIMAL` 或以分为单位的整数，不使用浮点数。
- 所有业务表包含 `id`、`created_at`、`updated_at`，必要时包含 `version` 乐观锁。
- 重要状态变更使用独立日志表，不依赖覆盖更新后的最终值。

## 10. AI 与语音能力设计

## 10.1 农户语音表达流程

```text
录音/上传
  → 语音识别
  → 方言与口语纠错
  → 提取时间、地块、作物、动作、数量和异常
  → 缺失信息追问
  → 农户试听/确认
  → 保存原始转写和确认文本
  → 提交村级审核
```

### 设计原则

- 原始语音、原始转写、AI 整理稿和人工修改稿分开保存。
- 每个生成句子应尽量关联来源生产记录。
- AI 不得把“农户未提及”推断成事实。
- 涉及农药、化肥、绿色/有机认证、治疗功效和产量时必须人工确认。
- AI 请求失败时，农户仍能保存原始录音和手工文本。

## 10.2 AI 生成场景

- 单条生产记录整理。
- 商品短介绍和详情页故事。
- 农户公开页简介。
- 微信朋友圈/群聊分享文案。
- 视频字幕和标题建议。
- 管理后台的敏感词、夸大宣传和信息缺失提示。

## 10.3 AI 质量评估

建立至少 100 条经村民和运营确认的测试样本，持续评估：

- 事实一致性。
- 农业名词识别准确率。
- 方言/口音转写可读性。
- 必填字段提取完整率。
- 夸大或虚构发生率。
- 农户一次确认通过率。
- 平均生成耗时和失败率。

## 11. 安全、隐私与合规

- 手机号、收货地址、身份信息加密或脱敏存储与展示。
- 登录、验证码、上传、AI 生成和订单接口实施限流。
- 管理操作使用细粒度权限和二次确认。
- 核款、退款、收款码变更和导出属于高风险操作，必须审计。
- 上传文件不得直接使用用户原始文件名作为访问路径。
- 对象存储私有桶通过短期签名 URL 访问；公开内容单独发布。
- 农户上传前确认内容真实性和公开授权，语音转写前获得明确同意。
- 对外页面不得展示完整手机号、身份证、精确私人住址等敏感信息。
- 收款码正式上线前必须确认收款主体、财税和经营资质边界。
- 所有景点图片、农户素材和视频在正式公开前确认版权或授权。

## 12. 非功能要求

### 性能

- 公开列表 API P95 小于 500ms，核心写接口 P95 小于 800ms（不含 AI 和转码任务）。
- 首屏 LCP 目标小于 2.5 秒，图片使用响应式压缩和懒加载。
- 大文件上传采用分片或客户端直传，避免占满 Spring Boot 线程和带宽。

### 可用性

- V1 服务可用性目标 99.5%。
- AI、短信和物流为可降级依赖，故障不应阻断原始记录保存。
- 数据库每日备份，关键订单与审计日志设置更长保留周期。

### 多端兼容

- 手机宽度 360px 起可使用所有核心流程。
- 覆盖微信内置浏览器、主流 Android 浏览器、iOS Safari 和桌面 Chrome/Edge。
- 农户入口优先大字号、大触控区域、低文字密度和语音引导。

### 可观测性

- 使用 Actuator 提供健康、指标和版本信息。
- 统一请求 ID、结构化日志、慢接口、异常率和任务队列监控。
- 对订单状态异常、媒体处理失败、AI 失败率和对象存储容量设置告警。

## 13. 开发阶段与里程碑

以下计划按 1 名前端、2 名后端、1 名测试/产品协同估算，总周期约 10—12 周。资源变化时按优先级裁剪，不压缩安全和订单状态验证。

### 阶段 0：工程与基础设施（第 1 周）

交付内容：

- 前端路由和公共组件拆分，建立公开、农户、后台三类页面结构。
- Spring Boot 分层、统一返回、异常处理、分页和 OpenAPI。
- MySQL、Flyway、开发环境配置和基础 CI。
- 登录、RBAC、审计框架和对象存储适配接口。

验收标准：

- 本地一条命令完成数据库初始化和服务启动。
- 前后端独立开发、Maven 集成构建和 Docker 构建均通过。
- 数据库迁移可重复执行且可在全新环境完成初始化。

### 阶段 1：公开门户与内容后台（第 2—3 周）

交付内容：

- 村庄、路线、景点、旅行计划、民宿、采摘、农品和联系方式数据模型。
- 公开查询 API、后台 CRUD、分页、排序、上下线和预览。
- 图片上传、缩略图和基础媒体管理。
- 将原型静态数据替换为真实 API。

验收标准：

- 后台新增或修改内容后，无需发版即可在公开页展示。
- 所有列表具备分页、空状态、错误状态和移动端布局。
- 下线内容不再出现在公开接口，但历史订单快照不受影响。

### 阶段 2：农户、地块与真实生产记录（第 4—5 周）

交付内容：

- 农户认证、地块、农品、SKU 和生产记录。
- 照片、视频、语音上传及媒体处理状态。
- 生产记录提交、审核、驳回、补充和发布。
- 农户公开页和商品生产时间线。

验收标准：

- 农户只能访问本人数据。
- 未审核记录不能公开，也不能进入正式 AI 文案素材。
- 上传失败可以重试，不产生重复记录或孤立媒体。

### 阶段 3：语音与 AI 表达助手（第 6—7 周）

交付内容：

- 录音、语音转写、结构化信息提取和缺失项追问。
- 商品介绍、农户故事、分享文案和 TTS 试听。
- AI 输入来源、模型版本、输出、人工修改和审核记录。
- 内容安全、事实一致性检查和失败降级。

验收标准：

- 原始语音和 AI 文案可追溯。
- AI 不能直接绕过人工确认发布。
- 建立评测集并达到项目约定的准确率和事实一致性阈值。

### 阶段 4：订单、人工核款与发货（第 8—9 周）

交付内容：

- 商品 SKU、价格快照、订单创建和客户查询。
- 收款码版本、转账报告、人工核款和凭证。
- 农户备货、统一发货、物流录入和状态通知。
- 取消、退款登记、售后和完整状态日志。

验收标准：

- 重复点击不会重复创建订单或重复推进状态。
- 未确认到账不能进入备货状态。
- 所有高风险状态变更均有权限校验和审计记录。
- 历史订单可还原下单时的商品、价格、地址和收款配置。

### 阶段 5：运营完善与多端优化（第 10 周）

交付内容：

- 运营看板、待办、筛选、导出和异常订单。
- 移动端、微信浏览器和弱网优化。
- 分享卡片、SEO、访问统计和内容更新提醒。
- 帮助中心、农户引导和人工协助入口。

验收标准：

- 关键页面完成目标设备兼容测试。
- 运营人员可以独立完成内容、审核、核款和发货操作。

### 阶段 6：安全、压测、试点和上线（第 11—12 周）

交付内容：

- 安全测试、权限越权检查、文件安全和敏感信息检查。
- API 压测、静态资源缓存、数据库索引和慢查询治理。
- 数据备份恢复演练、监控告警和运维手册。
- 选取少量农户、商品和订单进行村内试点。

验收标准：

- P0/P1 缺陷清零。
- 完成备份恢复、故障降级和回滚演练。
- 村庄运营、农户代表和项目负责人共同签署 UAT 结果。

6. 同步 CodeGraph 并执行 `git diff --check`。

生成的 `static/`、`node_modules/` 和 `target/` 不提交 Git。

```bash
java -jar backend/target/nanpo-window-backend-0.1.0-SNAPSHOT.jar
```

```bash
docker build -t nanpo-window .
```

## 17. Agent 开发操作规范

本节是对根目录 `AGENTS.md` 的业务补充；出现冲突时以 `AGENTS.md` 和更高层指令为准。

1. 修改前先执行 `codegraph explore` 定位代码、调用关系和影响面。
2. 前端页面与状态放在 `frontend/`，后端业务和数据放在 `backend/`，禁止把新的业务数据继续硬编码到原型常量中。
3. 每个前端功能都必须定义对应 API 契约、加载状态、空状态、错误状态和权限行为。
4. 每个后端写操作必须包含输入校验、权限、事务、幂等或并发策略、审计和测试。
5. 数据库变更必须新增 Flyway 迁移，不修改已经发布的迁移文件。
6. 订单和内容状态只能通过领域命令迁移，禁止任意覆盖状态字段。
7. AI 生成必须保存来源和人工确认，不得把模型输出直接作为真实事实发布。
8. 媒体必须通过统一媒体服务上传和引用，不在业务表重复保存文件地址逻辑。
9. 完成编码后运行 `./scripts/verify.sh`，失败时不得提交。
10. 验证后检查 `git status`，不得提交静态构建产物、依赖目录、密钥、IDE 文件或本地数据库。
11. 同步更新 API 文档、数据库迁移、测试、CodeGraph 和本开发计划中的相关决策。
12. 提交信息要说明一个完整业务变化；推送远程仓库前确认用户授权。

## 18. Definition of Done

一个功能只有同时满足以下条件才算完成：

- 产品流程、异常流程和权限边界明确。
- 前端多端界面完成，包含加载、空、错误和无权限状态。
- 后端 API、数据库迁移、校验、审计和错误码完成。
- 单元测试和集成测试通过，关键流程有 E2E 或可重复验收脚本。
- 敏感信息、上传文件和操作权限经过检查。
- API/README/开发计划文档已更新。
- `./scripts/verify.sh` 完整通过。
- CodeGraph 已同步，Git 工作区只包含应提交的源文件。

## 19. 主要风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 农户不会操作复杂表单 | 记录提交率低 | 语音优先、大按钮、逐步问答、人工代录 |
| AI 生成虚构或夸大内容 | 信任和合规风险 | 只读审核记录、引用来源、人工确认、敏感规则 |
| 收款码人工核款出错 | 资金和发货纠纷 | 唯一订单号、备注规则、双重确认、完整审计 |
| 视频和语音占用大量存储 | 成本与性能问题 | 大小限制、转码、生命周期和归档策略 |
| 景点路线信息过期 | 游客体验受损 | 来源、有效期、复核时间和后台过期提醒 |
| 农户隐私或地块信息泄露 | 隐私与安全风险 | 数据分级、脱敏、公开范围确认 |
| 图片版权不明确 | 对外发布风险 | 素材授权台账、上线前逐项核验 |
| 单体应用后期模块耦合 | 研发效率下降 | 明确模块边界、领域服务、事件解耦，暂不急于微服务 |

## 20. 启动开发前待确认事项

以下问题不阻塞工程骨架建设，但应在对应阶段开始前确认：

1. 正式收款主体、收款码管理人、财税和售后责任主体。
2. 农户账号是自助注册、管理员创建，还是两者并行。
3. 正式使用 MySQL、自建对象存储还是云对象存储。
4. 语音识别、生成模型、文字转语音的供应商与成本上限。
5. 是否需要短信验证码和订单状态短信，还是先使用人工电话/微信。
6. 物流信息仅人工录入，还是接入快递查询服务。
7. 生产记录、语音、视频和订单数据的保留周期。
8. 景点图片、农户素材、收款码和个人信息的公开授权流程。
9. 首批试点农户、农品、民宿和采摘项目名单。
10. V1 上线域名、HTTPS、服务器和备份责任人。
